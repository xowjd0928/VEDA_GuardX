## 1. CameraTuner philosophy — corrected (respect the user's encoder choices)

**What changed:** the tuner used to force `CBR` + `GOV = 1×fps` on the grid profile. It now
enforces **only the settings that genuinely hurt latency** — `DynamicGOVEnable`,
`SmartCodecEnable`, `DynamicFPSEnable` off (+ WiseStream off) — and **leaves
`BitrateControlType` (CBR/VBR) and `GOVLength` to whatever you configured**.

**Why:** we re-examined CBR vs VBR for latency and the old assumption was over-applied:

- **Encoder latency:** VBR can be *lower* — CBR runs a rate-control buffer that adds delay;
  VBR ships each frame straight out.
- **Network latency:** CBR is steadier (no bitrate spikes), but on a **low-bitrate LAN**
  stream the spikes are nowhere near congesting the link, so the benefit is negligible.
- **GOV length:** has **no steady-state latency effect** at all (P-frames decode
  immediately); it only changes post-loss *recovery* time.

**Result:** profile6 restored to your **VBR / GOV=15**, and verified the tuner no longer
clobbers it (reports "0 requests" on launch).

## 2. Smoothness metric — added

Latency alone doesn't tell you if video *looks* smooth. The backends now log, per channel
every 5 s:

- **effective fps** (dropped frames if < 30),
- **jitter** = stddev of frame-arrival gaps (ideal ~5–10 ms; 33 ms = one frame interval),
- **max gap** = worst single stutter.

`analyze_latency.py` summarizes it alongside latency. Present in both the GStreamer and
FFmpeg backends (same log format).

## 3. Bitrate A/B (1024 vs 2048 kbps, profile6 800×448)

| | 1024 kbps | 2048 kbps |
|---|---|---|
| Latency median | 167 ms | 206 ms (≈ flat — link noise) |
| Smoothness jitter | 47 ms | 58 ms |
| Worst stutter | 633 ms | 922 ms |

**Finding:** doubling bitrate **did not change latency** (bitrate is bytes; the pipeline
counts frames) but made smoothness **slightly worse** — bigger I-frame bursts open bigger
delivery gaps. It buys **quality** (a visual call). **Chosen: 1024** at 800×448.

## 4. FFmpeg decode backend — implemented ⭐

New third `VideoBackend` (`ffmpeg_backend.h/.cpp`), selectable via
`QSettings video_backend = ffmpeg`. Decodes RTSP directly with **libavformat + libavcodec**
instead of QMediaPlayer/GStreamer — full control over buffering.

- Low-latency demux: `fflags=nobuffer`, `flags=low_delay`, `max_delay=0`,
  `reorder_queue_size=0`, `AV_CODEC_FLAG_LOW_DELAY`, no frame threading.
- Decode thread → `sws_scale` to BGRA → `QImage`, newest-frame-wins render.
- Exponential-backoff reconnect + visible status; per-channel smoothness logging.
- `rtsp_transport` (udp/tcp) honored from QSettings.
- FFmpeg dev libs ship **inside the GStreamer MSVC install** — CMake finds them under the
  same root and gates the backend on `HAVE_FFMPEG`.

**Verified working:** all 4 channels, correct render + detection-box overlay, low latency
(OSD = real time), and smoothness *better* than GStreamer in tonight's tests (jitter
15–19 ms at 800×448).

> Known gap: the FFmpeg path has **no RTCP-NTP `glass-to-display` metric** yet (smoothness
> only). Latency on that path is currently eyeballed via the camera OSD.

## 5. 4×1080p "ultra" test — the bottleneck is the Wi-Fi, not the PC

Pushed to **4 × 1080p @ 30**. Key findings (and a correction to an earlier claim):

- **8 Mbps × 4 = 32 Mbps** saturated the **57.8 Mbps Wi-Fi** → streams starved (0.4–24 fps,
  multi-second freezes). **This was bandwidth, not CPU.**
- ❌ **Correction:** the earlier "software decode can't do 4×1080p — CPU wall" was **wrong**.
  Measured: FFmpeg software decode of 4×1080p is only **~1.4 CPU cores** (16.9 % of an
  8-core machine). The PC is not the limit.
- **ch2** dropping to 15 fps all night was also **bandwidth/link-related**, not a permanent
  camera fault — it recovered to ~30 fps once the bitrate fit the link.

**The fix for true 4×1080p ultra:** the **1 Gbps wired Ethernet** (이더넷 2), where
4×8 Mbps is trivial. On Wi-Fi, keep the aggregate bitrate modest.

## 7. UDP vs TCP (FFmpeg, profile6 1080p, back-to-back)

| | UDP | TCP |
|---|---|---|
| ch0/1/3 fps | ~28.6 | **~30.5** |
| ch0/1/3 jitter | 35 ms | **30 ms** |
| Worst stutter | 757 ms | **430 ms** |
| ch2 fps | **28.2** | 15.1 |
| ALL fps | 28.4 | 26.5 |

- **TCP is smoother on the healthy channels** on this calm link (retransmits → no dropped
  frames → cleaner 30 fps, fewer big stutters).
- **UDP is more uniform** (ch2 works) but drops packets → occasional bigger stutters.
- **ch2** flips (28 fps UDP → 15 fps TCP) — channel-specific head-of-line blocking under TCP.
- **Caveat:** TCP's smoothness win holds only while the link is calm. On a stressed/lossy
  link TCP snowballs into multi-second backlog (measured 1481 ms on earlier jittery nights);
  UDP stays live by dropping. UDP remains the robust low-latency default.

**Set to: TCP** (per request, for this deployment's calm link).
